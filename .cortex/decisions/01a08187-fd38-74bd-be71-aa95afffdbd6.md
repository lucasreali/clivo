CLIVO adopted @tanstack/react-table v9 and confined it to a single primitive, src/shared/ui/DataTable.tsx. Features never import @tanstack/react-table — the same rule already in force for Base UI: a screen builds columns with columnsFor<Row>() (a re-export of createColumnHelper bound to the app's one feature set) and renders <DataTable columns rows rowId />.

Before this, every listing was a hand-rolled CSS grid: a `const COLUMNS = "grid-cols-[1.7fr_1fr_160px]"` string duplicated between the header div and each row div, six times across the codebase, with no table semantics at all (no <table>, no columnheader roles), no sorting and no pagination.

What the primitive owns: semantic <table>/<thead>/<tbody> markup, the header styling, click-to-sort headers (Phosphor caret marks), an optional pager, and the pending/empty slots. Column layout travels in the column's meta ({ width, align }) and is applied through a <colgroup> on a table-fixed table, replacing the grid-template strings. verticalAlign="top" exists for rows with a tall control (ClinicParameters); highlighted(row) marks a selected row (TeamPanel).

Feature set registered once in the primitive: rowSortingFeature + createSortedRowModel and rowPaginationFeature + createPaginatedRowModel, with sortFns { alphanumeric, basic, datetime, text } registered so v9's auto sort-fn detection works, and columnMeta declared via metaHelper<ColumnLayout>() instead of global declaration merging. When pageSize is omitted the initial pageSize is Number.MAX_SAFE_INTEGER, because registering rowPaginationFeature would otherwise silently cap every table at 10 rows.

Sorting and pagination are client-side: the API neither pages nor sorts (SearchCustomersQuery is `{ name?: string }` — no page/size/sort anywhere in the generated spec). Pagination is opted into per screen with pageSize; only CustomerList and ClinicList (12 rows/page) use it today.

Migrated: CustomerList, ClinicList, TeamPanel, ClinicModules, ClinicParameters, and both listings in InvoiceDetail (linhas do atendimento, pagamentos registrados). Deliberately left alone: CustomerHistory (stacked multi-line cards, not tabular), the module-activation history panel in ClinicModules, ParametersPanel (a 2-column grid of controls), DayPanel/WeekAgenda and EncounterRecord.

Supporting change: ClinicCatalog and ModuleCatalog gained listed() (replacing map(), which no caller needed once cells render rows) so a first-class collection can feed the table, and useClinicCatalog/useClinicModules now memoize the catalog on the query data so the table's row identity is stable across renders.

Rejected: adopting TanStack Table only for a future reports module while leaving the existing lists on CSS grids — a single unmigrated listing would break the reuse premise the project is built on. Also rejected: styling a <table> with display:grid to keep the fr units exactly, since that drops the implicit ARIA table role; percentage/px widths in a colgroup were preferred.

Note: @tanstack/react-table does NOT draw charts. The future reports module needs a separate charting decision (Recharts is the pragmatic default; @tanstack/react-charts is effectively unmaintained).
